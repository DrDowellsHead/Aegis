# Aegis

**Разработчик:** [DrDowellsHead](https://github.com/DrDowellsHead) · **Сотрудничество и коммерческие заказы:** [CONTACT.md](CONTACT.md) · **Обратная связь:** [GitHub Issues](https://github.com/DrDowellsHead/Aegis/issues/new?template=collaboration.md)

Aegis — учебно-практическая платформа мониторинга инфраструктуры на Go.
Разработка идёт в `develop`; `main` предназначена для проверенных версий.

## Текущий этап

Работают диагностический HTTP-сервер, HTTP-проверки, локальный агент метрик и gRPC-передача с TLS и проверкой токенов. Полная платформа (агенты, API истории, уведомления)
разрабатывается поэтапно. Реализованные возможности и ограничения описываются
по мере появления кода — план не является списком готовых функций.

## План

1. CLI, жизненный цикл сервера, HTTP-проверки доступности.
2. Агент со сбором CPU, RAM, диска и сети на Windows, macOS и Linux.
3. Защищённая передача измерений через gRPC.
4. PostgreSQL, миграции и локальный API истории.
5. Инциденты, уведомления и наблюдаемость самой системы.
6. Проверка отказов, производительности и развёртывание на одном VPS.

Архитектура: [ADR 0001](docs/adr/0001-foundation.md).
Рабочий процесс: [CONTRIBUTING.md](CONTRIBUTING.md).

## Реализовано: первый рабочий этап

- `aegis version` — версия исполняемого файла.
- `aegis serve` — локальный HTTP-сервер, `/healthz`, JSON-журналы,
  завершение по Ctrl+C/SIGTERM с ограниченным временем ожидания.
- `aegis check --url http://127.0.0.1:8080/healthz` — однократная
  HTTP-проверка с таймаутом, JSON-результатом и кодом завершения.
- CI: тесты с обнаружением гонок на Windows/macOS/Linux; сборка шести архивов.
- Процесс подготовки черновика релиза по тегу из истории main.

[Установка и запуск](docs/installation.md) · [Как выпускать релизы](docs/releases.md)

```sh
go run ./cmd/aegis serve
# В другом терминале:
go run ./cmd/aegis check --url http://127.0.0.1:8080/healthz
```

gRPC-передача защищена TLS и токенами. PostgreSQL сохраняет измерения с проверкой
повторов. API истории реализован для локального доступа; уведомления ещё не реализованы.

## Локальный агент метрик

```sh
go run ./cmd/aegis collect --disk .
go run ./cmd/aegis agent --disk . --interval 5s --count 3
```

`collect` выводит один JSON-объект, `agent` — по объекту на строку.
Измеряются загрузка CPU, память, файловая система выбранного пути и счётчики
байтов отдельных сетевых интерфейсов. Счётчики сети не являются скоростью.
При ошибке одной группы другие сохраняются; отсутствующие значения — `null`,
описание ошибки — в `errors`. Подробности: [метрики](docs/metrics.md).

## Защищённая отправка метрик (этап 3.2)

Для локальной демонстрации запустите следующие команды в каталоге проекта.
Команда `cert` выпускает **демонстрационные** сертификаты для адреса 127.0.0.1.
Команда `provision` создаёт пару: закрытые данные агента и реестр разрешённых агентов.

```sh
go run ./cmd/aegis cert --host 127.0.0.1 --ca-cert local-ca.crt --tls-cert local-server.crt --tls-key local-server.key
go run ./cmd/aegis provision --agents-file local-agents.json --credentials local-agent.json
```

После настройки PostgreSQL и выполнения миграций (см. этап 3.4)
в первом терминале запустите сервер:

```sh
go run ./cmd/aegis receive --listen 127.0.0.1:9090 --tls-cert local-server.crt --tls-key local-server.key --agents-file local-agents.json
```

Во втором терминале отправьте одно измерение:

```sh
go run ./cmd/aegis send --server 127.0.0.1:9090 --credentials local-agent.json --ca-cert local-ca.crt --disk .
```

Ожидаемый ответ включает `"received": true`, `"durable": true` и
уникальный `measurement_id`. Данные сохраняются в PostgreSQL.
Команды `collect` и `agent` по-прежнему работают локально, без подключения.

Для нескольких компьютеров копируйте ТОЛЬКО соответствующий закрытый
`agent.json` и публичный CA-сертификат на агент, оставляя `agents.json`
и закрытый TLS-ключ на сервере. По умолчанию сервер слушает loopback;
публикация порта требует настройки firewall, прав доступа и аудита.
Адрес клиента обязан совпадать с именем/IP в сертификате (SAN).
Регистрация следующего агента требует перезапуска сервера для перечитывания реестра.
Не запускайте две регистрации одновременно в один файл.

На Unix файлы с токенами и приватными ключами создаются с правами 0600.
На Windows дополнительно проверьте ACL, чтобы секреты были доступны
только вашей учётной записи/службе. Никогда не публикуйте их в GitHub.
Самоподписанный демонстрационный CA не предназначен для серьёзного развёртывания.
Передача защищена; отдельная команда `forward` реализует очередь и повторы.
Ротация и отзыв токенов, а также административный интерфейс ещё не реализованы.

Контракт: [telemetry.proto](api/proto/aegis/telemetry/v1/telemetry.proto).
Документы: [ADR 0003](docs/adr/0003-telemetry-contract.md),
[ADR 0004](docs/adr/0004-agent-identity-and-tls.md).

## Очередь и повторная отправка (экспериментальный этап 3.3)

Вместо одноразовой команды `send` можно запустить длительный режим `forward`:

```sh
go run ./cmd/aegis forward --server 127.0.0.1:9090 --credentials local-agent.json --ca-cert local-ca.crt --queue-dir /path/to/private/spool --interval 5s --max-queue-mb 64
```

На Windows замените `/path/to/private/spool` на подходящий путь либо вообще
опустите `--queue-dir`: тогда очередь будет храниться в директории конфигурации
пользователя, отдельно для каждого UUID агента. Для демонстрации можно указать
`--count 3`, чтобы собрать три измерения и попытаться отправить все три.

**Важно:** теперь только `durable=true` после записи в PostgreSQL разрешает
удалить подтверждённую запись из локальной очереди. Потерянное подтверждение
вызывает повтор с тем же ID; сервер не создаёт дубликат.
При переполнении агент сообщает об ошибке и останавливает сбор; старые записи
не стираются. Не запускайте два процесса с одной очередью одновременно.

[ADR 0005: дисковая очередь, повторные попытки и ограничения](docs/adr/0005-disk-queue-and-retry.md).

## PostgreSQL: миграции и устойчивое подтверждение (этап 3.4)

Для локального ознакомления нужен PostgreSQL 17+ (проверяем CI на 17).
Например, с Docker (пароль исключительно демонстрационный):

```sh
docker run --name aegis-postgres -d -e POSTGRES_USER=aegis -e POSTGRES_PASSWORD=dev-only-change-this -e POSTGRES_DB=aegis -p 127.0.0.1:5432:5432 -v aegis-pgdata:/var/lib/postgresql/data postgres:17
```

В Windows PowerShell укажите строку подключения через переменную окружения
терминала (не храните реальный пароль в git):

```powershell
$env:AEGIS_DATABASE_URL = "postgres://aegis:dev-only-change-this@127.0.0.1:5432/aegis?sslmode=disable"
go run ./cmd/aegis migrate
go run ./cmd/aegis receive --listen 127.0.0.1:9090 --tls-cert local-server.crt --tls-key local-server.key --agents-file local-agents.json
```

`sslmode=disable` допускается только для локального демонстрационного PostgreSQL
на loopback. К удалённой базе нужно подключаться по TLS с проверкой сервера.
На машине агента PostgreSQL не требуется. Отдельная команда `forward`
сохраняет измерения на диск, отправляет их и удаляет **только после**
подтверждения фиксации в PostgreSQL. Миграции выполняются вручную;
при старте `receive` проверяет наличие схемы и настройки записи.

В PostgreSQL метрики сохраняются как protobuf BYTEA, а первичный ключ
`(agent_id, measurement_id)` защищает от дубликатов.
Узнать число измерений можно SQL-запросом:

```sql
SELECT agent_id, count(*) FROM aegis_measurements GROUP BY agent_id;
```

Полное описание: [ADR 0006](docs/adr/0006-postgresql-durable-ack.md).

## История измерений через HTTP (этап 3.5)

Агент по-прежнему отправляет метрики gRPC-серверу `receive`.
Отдельная команда `history` даёт доступ к сохранённым измерениям
только через локальный интерфейс и **отдельный операторский токен**.
Нельзя использовать для этого токен агента.

Для Windows PowerShell (после настройки PostgreSQL из этапа 3.4):

```powershell
$env:AEGIS_DATABASE_URL = "postgres://aegis:dev-only-change-this@127.0.0.1:5432/aegis?sslmode=disable"
go run ./cmd/aegis migrate
$env:AEGIS_HISTORY_TOKEN = "demo-only-replace-with-a-random-32byte-secret"
go run ./cmd/aegis history --listen 127.0.0.1:8081
```

Лучше использовать отдельную SQL-учётную запись с правами только на SELECT
по таблицам `aegis_measurements` и `aegis_schema_migrations`, а не роль,
которой `receive` пишет в базу. В отдельном PowerShell-терминале укажите
те же `AEGIS_HISTORY_TOKEN` и UUID из `local-agent.json`:

```powershell
$agentId = (Get-Content local-agent.json | ConvertFrom-Json).agent_id
$headers = @{Authorization = "Bearer $env:AEGIS_HISTORY_TOKEN"}
Invoke-RestMethod -Headers $headers -Uri "http://127.0.0.1:8081/api/v1/measurements?agent_id=$agentId&limit=5"
```

Если запрос вернул `next_cursor`, следующую страницу можно получить так:

```powershell
$page = Invoke-RestMethod -Headers $headers -Uri "http://127.0.0.1:8081/api/v1/measurements?agent_id=$agentId&limit=5"
if ($page.has_more) {
    $cursor = [uri]::EscapeDataString($page.next_cursor)
    Invoke-RestMethod -Headers $headers -Uri "http://127.0.0.1:8081/api/v1/measurements?agent_id=$agentId&limit=5&cursor=$cursor"
}
```

Поддерживаются `from` (включительно), `to` (исключительно) в RFC 3339,
`limit` (1..100) и курсорная пагинация. Старые снимки из PostgreSQL
преобразуются из Protobuf в JSON, сохраняя структуру CPU, памяти,
диска и сети и сообщения о частичных ошибках.

**Безопасность:** текущее HTTP API слушает только 127.0.0.1/::1.
Не ставьте перед ним публичный прокси и не публикуйте порт 8081
в интернет: для удалённого доступа понадобятся TLS, надёжная
административная аутентификация и политика авторизации.

Подробнее: [ADR 0007](docs/adr/0007-history-api.md).

## Временные ряды и агрегаты для графиков (этап 3.6)

Сначала на сервере выполните миграцию 004 и **возобновляемое заполнение
проекций старых записей**, иначе графики до обновления схемы будут пустыми:

```powershell
go run ./cmd/aegis migrate
go run ./cmd/aegis backfill --batch-size 100
```

В обоих случаях требуется `AEGIS_DATABASE_URL` с полномочиями на запись.
Команда backfill поддерживает `--max-records N` для проверки небольшими
порциями и безопасно повторяется после прерывания.

С уже запущенной командой `aegis history` запросите временной ряд:

```powershell
$agentId = (Get-Content local-agent.json | ConvertFrom-Json).agent_id
$headers = @{ Authorization = "Bearer $env:AEGIS_HISTORY_TOKEN" }
$from = [uri]::EscapeDataString("2026-10-20T12:00:00Z")
$to = [uri]::EscapeDataString("2026-10-20T13:00:00Z")
Invoke-RestMethod -Headers $headers -Uri "http://127.0.0.1:8081/api/v1/series?agent_id=$agentId&from=$from&to=$to&step=5m"
```

`step`: 1m, 5m, 15m, 1h, 6h, 24h; максимум 500 интервалов
и 90 дней за запрос. Ответ содержит `points`, их время `at`,
`cpu_avg/min/max`, `memory_avg`, `disk_avg`, а также отдельные счётчики
измерений. Для диска **обязательно указывайте** `disk_path`, например
`&disk_path=C%3A%5C` для `C:\\` или `&disk_path=%2F` для `/`.
Без него `disk_avg` будет `null` — усреднять разные файловые системы нельзя.

Пустые интервалы не заполняются нулями. Пока API доступен только локально.

[ADR 0008 — временные ряды](docs/adr/0008-time-series.md) ·
[Полный план Aegis](docs/roadmap.md).

## Реестр агентов и оценка состояния (этап 3.7)

Миграция 005 добавляет в PostgreSQL `aegis_agents`, но не переносит туда
секреты авторизации. Защищённый `agents.json` остаётся единственным
авторитетным списком разрешённых UUID. При каждом запуске `aegis receive`
этот список транзакционно синхронизируется с БД до начала приёма gRPC.

После `aegis migrate` **перезапустите** `receive` (с теми же
`--agents-file`, сертификатами и `AEGIS_DATABASE_URL`). Иначе
новые зарегистрированные, но ещё не отправлявшие метрики агенты
не появятся в PostgreSQL. API `history` использует уже существующий
`AEGIS_HISTORY_TOKEN` и продолжает слушать только 127.0.0.1/::1.

В другом терминале PowerShell с тем же операторским токеном:

```powershell
$headers = @{ Authorization = "Bearer $env:AEGIS_HISTORY_TOKEN" }
$result = Invoke-RestMethod -Headers $headers -Uri "http://127.0.0.1:8081/api/v1/agents?limit=100&offline_after=1m"
$result.items | Format-Table agent_id, status, last_contact_at, last_sample_at, os, arch
```

`online` — сервер получал подтверждённый аутентифицированный запрос
в течение `offline_after`, `offline` — не получал дольше,
`unknown` — ещё ни одного подтверждённого контакта. Это **не**
проверка фактического состояния включения компьютера. Время последнего
контакта задаёт PostgreSQL, а не агент; время последнего измерения
берётся из сообщения агента и может быть старым из-за накопленной очереди.

Запрос поддерживает `limit=1..200`, `cursor=UUID` и
`offline_after` (10s..24h). Если `has_more` — true, передайте
`next_cursor` в следующем запросе. Секреты никогда не возвращаются.

Подробнее: [ADR 0009](docs/adr/0009-agent-registry.md).

## Retention и объём PostgreSQL (этап 3.8)

После обновления `develop` выполните `aegis migrate` с корректным
`AEGIS_DATABASE_URL`. Миграция 006 добавляет индекс для ограниченного
по времени удаления. Она не удаляет измерения автоматически.

Сначала проверьте размер базы и потенциальные кандидаты на очистку:

```powershell
go run ./cmd/aegis storage
go run ./cmd/aegis retention --days 30
```

Команда `retention` **по умолчанию только считает** подходящие строки.
Для фактического удаления нужны `--apply` и явно указанный scope:

```powershell
$agentId = (Get-Content local-agent.json | ConvertFrom-Json).agent_id
go run ./cmd/aegis retention --days 30 --agent-id $agentId --apply --batch-size 500 --max-delete 10000
```

Для очистки всех агентов потребуется вместо `--agent-id`
написать `--all-agents`. Без явного выбора scope удаление
не запустится. Срок хранения задаётся `--days` (7..3650 дней).
Каждый запуск удаляет максимум `--max-delete` строк (по умолчанию
10 000) пакетами (по умолчанию 500). Для продолжения запустите
команду повторно; она выведет количество удалённых строк в JSON.

**До --apply сделайте бэкап.** Пример для локального PostgreSQL
в Docker; экспортирование в файл вне контейнера через `docker cp`
сохраняет бинарный `pg_dump` без повреждения PowerShell-перенаправлением:

```powershell
docker exec aegis-postgres pg_dump -U aegis -d aegis -Fc -f /tmp/aegis-before-retention.dump
docker cp aegis-postgres:/tmp/aegis-before-retention.dump ./aegis-before-retention.dump
```

Проверьте, что файл на месте, и протестируйте восстановление в
**отдельной тестовой базе**, прежде чем удалять историю в production.
Не публикуйте дампы с телеметрией и секретами.
Важно: `DELETE` в PostgreSQL обычно НЕ уменьшает файл таблицы сразу.
Autovacuum освободит страницы для повторного использования; реальная
ёмкость диска может остаться прежней. Обычный `VACUUM (ANALYZE)`
не выполняется автоматически и не обещает возврата места ОС.

Очистка использует `received_at`, а не часы агента `started_at`.
Список зарегистрированных агентов и сведения о последнем контакте
не удаляются при очистке истории. Полный разбор безопасности,
ограничений и MVCC: [ADR 0010](docs/adr/0010-retention.md).

## Административные команды, диагностика и аудит (этап 3.9)

После `git pull origin develop` с учётной записью PostgreSQL, имеющей
права на миграции, запустите `aegis migrate`: миграция 007 создаёт
таблицу журнала административных операций.

Опционально создайте несекретный конфигурационный файл по
[примеру](examples/admin.json). Укажите путь в `AEGIS_ADMIN_CONFIG`:
никаких токенов, паролей или DSN в этом JSON быть не должно.
CLI-флаги имеют приоритет над значениями по умолчанию из файла.

```powershell
$env:AEGIS_ADMIN_CONFIG = ".\examples\admin.json"
$env:AEGIS_OPERATOR = "operator-local"
go run ./cmd/aegis config
go run ./cmd/aegis doctor
go run ./cmd/aegis audit --limit 20
```

`doctor` возвращает JSON с результатом проверок без паролей или
самой строки подключения. При неготовности возвращает exit code 1,
а не исправляет схему автоматически.

Команды `retention --apply` и `backfill` требуют доступный журнал
аудита; если начало операции невозможно записать, они не выполняют
изменений. После успешного запуска:

```powershell
go run ./cmd/aegis retention --days 30 --agent-id $agentId --apply
go run ./cmd/aegis audit --limit 10
```

Журнал хранит статус `running/succeeded/failed/interrupted`, время,
метку оператора, область изменений и **коммитнутое число строк**.
Счётчик обновляется в той же PostgreSQL-транзакции, что и пакет
удалений или преобразований. Если процесс аварийно завершился,
`running` может остаться в журнале: это неопределённый статус
завершения, а не сообщение об успехе.

Метка `AEGIS_OPERATOR` задаётся самим оператором и пока не удостоверяет
реальную личность человека. Таблица аудита не является неизменяемой
или защищённой криптографической подписью. Миграции, операции с
приватными файлами и чтение данных ещё не покрыты единым аудитом.
На следующем этапе потребуется полноценная модель прав и сессий.

Подробности: [ADR 0011](docs/adr/0011-administration.md).

## Веб-панель: архитектура и каркас (этап 4.1)

В `web/` создан отдельный фронтенд на React, TypeScript и Vite. Пока это
**статический интерфейс без реальных данных и подключения к БД**:
панель показывает честное состояние «данные не подключены», разделы
Обзор / Агенты / Карточка агента / Инциденты (в планах) / Настройки
(в планах). Выдуманных метрик или HTTP-запросов к секретному API нет.

```powershell

```

не проксирует локальный API и не выполняет CORS-послаблений.

## Локальная панель агентов (этап 4.2)

Теперь `aegis dashboard` запускает **отдельный Go-сервер с браузерной
сессией**, по умолчанию на `127.0.0.1:8082`. Он обращается к PostgreSQL
на сервере и не передаёт `AEGIS_HISTORY_TOKEN` в JavaScript.

Перед запуском:
1. Установите Node.js 22+ и выполните `cd web; npm ci; npm run build; cd ..`.
2. Убедитесь, что `AEGIS_DATABASE_URL` указывает на БД после миграций
   и команда `aegis receive` синхронизировала зарегистрированные UUID.
3. Установите **отдельный сильный** `AEGIS_DASHBOARD_TOKEN`. Пример
   генерации в Windows PowerShell (токен не записывается в репозиторий):

```powershell
$bytes = New-Object byte[] 32
$rng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
$rng.GetBytes($bytes)
$rng.Dispose()
$env:AEGIS_DASHBOARD_TOKEN = [Convert]::ToBase64String($bytes)

go run ./cmd/aegis dashboard --listen 127.0.0.1:8082 --static-dir web/dist
```

Откройте **http://127.0.0.1:8082** и введите сгенерированный токен
панели. В другой PowerShell-сессии нужно предварительно задать
`AEGIS_DATABASE_URL` и `AEGIS_DASHBOARD_TOKEN` заново: переменные
окружения процесса не копируются между терминалами автоматически.
В браузере теперь доступны настоящая сводка состояний и список
агентов, страницы по UUID, ручное обновление и периодическое обновление
раз в 30 секунд в видимой вкладке.

Сервер ОБЯЗАТЕЛЬНО слушает только числовой loopback. Это **локальная
версия**, не готовая к публикации на VPS: текущая HTTP-сессия без HTTPS
не предназначена для внешней сети. Не открывайте порт 8082 через
публичный reverse proxy, SSH-туннель в общедоступную сеть или NAT.

Исполняемый Go-архив пока не содержит собранный React: `web/dist/`
строится отдельно. На будущих этапах добавим упаковку фронтенда
в дистрибутив и полноценный HTTPS/RBAC шлюз.

[OpenAPI веб-шлюза](api/openapi/dashboard-local-v1.yaml).

## Этап 4.4: произвольные интервалы, сравнение периодов и точные значения

На странице агента доступны периоды 1h/24h/7d и произвольное начало/конец

графиком. Подсказка содержит значения CPU/RAM/диска и время. Отсутствующие
бакеты не соединяются линиями и не заменяются нулями. Сравниваемая
средняя загрузка взвешена по числу фактических измерений в бакете.

Обновите `develop` и выполните из `web/` `npm ci`, `npm test`,
`npm run build`; затем запустите обычный `aegis dashboard`.
Новые SQL-миграции, порты или переменные среды не нужны.

## Этап 4.6 — HTTPS-панель с учётными записями и ролями

Существующий локальный запуск `aegis dashboard` по-прежнему поддерживается
**только на loopback**. Для доступа с другого компьютера предусмотрен
явный отдельный режим `--remote` с прямым TLS 1.3.

На сервере подготовьте защищённую папку с файлами учётных записей.
Команда `dashboard-user` считывает пароль **из stdin**, не из параметров
командной строки. Для PowerShell:

```powershell
# Из корня репозитория. Ввод пароля скрыт от окружающих.
function Add-AegisUser {
    param([string]$Name, [string]$Role)
    $secure = Read-Host "Пароль для $Name (16–72 байта)" -AsSecureString
    $ptr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
    try {
        $plain = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($ptr)
        $plain | go run ./cmd/aegis dashboard-user --file ./dashboard-users.json --username $Name --role $Role --password-stdin
    } finally {
        [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($ptr)
        Remove-Variable plain, secure -ErrorAction SilentlyContinue
    }
}
Add-AegisUser -Name operator -Role admin
Add-AegisUser -Name observer -Role viewer
```

Файл `dashboard-users.json` нельзя коммитить. На Linux и macOS выставьте
`chmod 600 dashboard-users.json`, ограничьте права директории.
На Windows настройте ACL так, чтобы читать файл мог только серверный
пользователь/администратор. Пароли в файле представлены bcrypt-хешами.

Потребуется **действительный TLS-сертификат** для имени панели; сервер
проверяет совпадение имени с SAN сертификата. Пример команды после
настройки DNS, firewall и TLS-сертификата (замените пути и домен):

```sh
aegis dashboard --remote --listen 0.0.0.0:8443 \
  --public-origin https://monitor.example.com:8443 \
  --users-file /etc/aegis/dashboard-users.json \
  --tls-cert /etc/letsencrypt/live/monitor.example.com/fullchain.pem \
  --tls-key /etc/letsencrypt/live/monitor.example.com/privkey.pem \
  --static-dir web/dist
```

Открывайте `https://monitor.example.com:8443`: обратите внимание на
**https**, точный домен и порт. Не ставьте HTTP-терминирующий прокси
перед этим режимом: сам Go-сервер обязан получать настоящее TLS-соединение.
Для продуктивной эксплуатации требуется автоматизация перевыпуска
сертификата и перезапуска сервиса после обновления сертификата.

`viewer` видит измерения всех агентов. `admin` дополнительно открывает
«Настройки», видит имена и роли пользователей и может отзывать их
сессии. Создание пользователей, изменение роли или пароля — только
через `dashboard-user` на машине сервера; после таких изменений нужно
перезапустить `dashboard` для применения файла и завершения старых сессий.

Для смены пароля существующего оператора добавьте `--replace` и передайте
новый пароль через stdin. Для удаления — `--remove` без пароля.
Удалить или понизить последнего администратора нельзя.

**Удалённая панель не эквивалентна завершённому production-аудиту.**
До открытия во внешнюю сеть проверьте DNS, доверенную цепочку TLS,
read-only учётную запись PostgreSQL, межсетевой экран, системные
обновления, резервное копирование и реальные интеграционные тесты.
Не используйте демонстрационные пароли или сертификаты в интернете.
Подробнее: [ADR 0017](docs/adr/0017-remote-dashboard.md).

## Этап 5.1: пороговые правила и гистерезис

После обновления `develop` выполните миграцию **008** с учётной записью
PostgreSQL, имеющей права на миграции, затем перезапустите `dashboard`:

```powershell
$env:AEGIS_DATABASE_URL = "postgres://aegis:dev-only-change-this@127.0.0.1:5432/aegis?sslmode=disable"
go run ./cmd/aegis migrate
cd web
npm ci
npm run build
cd ..
go run ./cmd/aegis dashboard --listen 127.0.0.1:8082 --static-dir web/dist
```

Пример содержит только **локальный демонстрационный** пароль:
не применяйте его в удалённой или рабочей инфраструктуре.

Откройте веб-панель, перейдите в **Правила**, укажите UUID
зарегистрированного агента, создайте правило и нажмите
**Проверить сейчас**. Для удалённой панели редактирование доступно только
роли `admin`, роль `viewer` может читать результаты.

Пример: CPU >=85% за последние 5 минут при минимум трёх реальных
измерениях; возврат в норму только после снижения среднего CPU
до <=70%. Между порогами состояние сохраняется. Последний замер
должен быть не старше 120 секунд. При недостатке или устаревании
данных статус станет `insufficient_data`, прежнее срабатывание
не сбрасывается.

У правила по диску обязательно указать **точный путь**
файловой системы (например, `/` или `C:\\`). Интервалы основаны
на времени измерения `started_at`, а не времени доставки в БД.

**Важно:** в 5.1 вычисление выполняется вручную кнопкой. Автоматические
обходы правил, heartbeat, создание инцидентов, подтверждение тревог и
уведомления будут разработаны позднее в фазе 5. Порог `firing`
пока не является настоящим инцидентом.

При использовании отдельной роли PostgreSQL с чтением только
`SELECT` теперь нужно ограниченно разрешить `INSERT/UPDATE/DELETE`
для таблиц `aegis_threshold_rules` и `aegis_rule_states`, а также
чтение `aegis_agents` и `aegis_measurements`. Не повышайте роль
до суперпользователя ради редактирования правил.

[ADR 0018](docs/adr/0018-threshold-rules.md) ·
[OpenAPI правил](api/openapi/threshold-rules-v1.yaml).

## Этап 5.2 — heartbeat и потеря связи

После обновления `develop` примените новую миграцию 009 на PostgreSQL:

```sh
aegis migrate
```

Перезапустите сервер `aegis receive` и Go Dashboard **до** обновления
агента, затем запустите агент с постоянной отправкой телеметрии:

```sh
aegis forward --server 127.0.0.1:9090 --credentials agent.json \
  --ca-cert ca.crt --interval 30s --heartbeat-interval 15s
```

Адрес, TLS-пути и файл credentials здесь только примеры: используйте
свои ранее выданные данные. Парольные файлы и токены не добавляйте в Git.
`--heartbeat-interval` поддерживает 1s..1h; значение `0` отключает
heartbeats для подключения к серверу старой версии.

На вкладке **Агенты** различаются **последний сигнал**, **Heartbeat** и
**Телеметрия**. Сигналы присутствия не являются измерениями CPU, RAM
или диска. Отсутствие телеметрии не делает живого агента offline, пока
сервер регулярно получает от него заверенные heartbeat. Значение
Offline означает отсутствие подтверждённого соединения в пределах
порогового интервала (по умолчанию 1 минута), а не доказательство
выключенного компьютера.

Heartbeat отправляется вне зависимости от очереди метрик, но только
пока запущен `aegis forward`; отдельный локальный `agent` и разовый
`send` heartbeat не отправляют. На шаге 5.2 **инциденты не создаются**,
а уведомления не рассылаются.

См. [ADR 0019](docs/adr/0019-heartbeat-liveness.md).

## Этап 5.3 — инциденты

Сначала обновите `develop` и выполните `aegis migrate`, чтобы
применить миграцию **010**. При этом старые уже сработавшие правила
(5.1) становятся открытыми инцидентами, не теряя прежнего состояния.

В веб-панели откройте **Правила** и нажмите **Проверить сейчас** для
нужного агента: при превышении появляется `open`; кнопка
**Подтвердить** на вкладке **Инциденты** переводит его в
`acknowledged`, сохраняя оператора и время. После возврата
метрики ниже порога восстановления следующая проверка правил
переведёт его в `resolved`. Повторная проблема получит новый ID.

На странице **Инциденты** также можно проверить доступность
зарегистрированного агента по времени последнего heartbeat/телеметрии.
Никогда не подключавшийся агент остаётся `unknown` — это не
инцидент потери связи. Если канал восстановится, следующая проверка
закроет ранее открытый инцидент.

Администратор может явно **Разрешить** инцидент вручную. Если
проблема сохранится, следующая проверка создаст новый инцидент;
подавления повторов ещё нет. Наблюдатели `viewer` могут только
читать. События переходов сохраняются в PostgreSQL.

**Ограничение этапа 5.3:** оценка порогов и потери связи выполняется
вручную — автоматического планировщика и рассылки уведомлений ещё
нет. События, возникшие и исчезнувшие между проверками, могут
остаться необнаруженными. Подробнее:
[ADR 0020](docs/adr/0020-incident-lifecycle.md).

## Этап 5.4 — cooldown, подавление повторов и эскалация

После получения ветки `develop` выполните `aegis migrate` с
правами изменения схемы PostgreSQL: миграция 011 добавляет настройки
и признаки приоритета инцидентов. Перезапустите Go Dashboard.

На вкладке **Инциденты** администратор может настроить:
- **Cooldown** (по умолчанию 300 секунд): после разрешения инцидента
  новые эпизоды той же проблемы временно подавляются; `0` отключает
  задержку. Сохраняются счётчик подавленных проверок и время
  последнего подавления.
- **Эскалацию** (по умолчанию 900 секунд): длительно открытый и
  неподтверждённый инцидент при очередной проверке становится
  `critical`. Записывается ровно одно событие `escalated`.

Состояния `open/acknowledged/resolved` не заменяются приоритетом:
`critical` — отдельное поле. Уже подтверждённый оператором
инцидент автоматически не повышается.

**Важно:** оценки пока выполняются вручную на страницах
**Правила** и **Инциденты**. Изменение интервала не запускает таймер:
повышение приоритета происходит только во время новой оценки,
даже если указанный срок давно прошёл. Почта, Telegram, webhook
и гарантированная доставка будут на следующих этапах.

[ADR 0021](docs/adr/0021-incident-noise.md).

## Шаг 5.5 — Email, Telegram и Webhook

1. Получите `develop` и запустите `aegis migrate` (миграция **012**).
2. Запустите один процесс `aegis notify` под supervisor/systemd с
   настройками **до** того, как начнут возникать новые события инцидентов.
   Без включённого маршрута события в очередь доставки не добавляются.
3. Откройте веб-панель → **Инциденты** → **Очередь уведомлений**:
   pending/retry/leased/sent/dead отражают сохранённые состояния.
4. Создайте инцидент кнопкой проверки правил/связи — worker отправит
   `opened` по настроенным каналам, затем `escalated` и `resolved`
   при соответствующих переходах.

**Пример для Telegram (PowerShell):**

```powershell
$env:AEGIS_DATABASE_URL = "<your PostgreSQL DSN>"
$env:AEGIS_TELEGRAM_TOKEN = "<your private bot token>"
go run ./cmd/aegis migrate
go run ./cmd/aegis notify --telegram-chat-id "-1001234567890"
```

**Пример для Email (PowerShell):**

```powershell
$env:AEGIS_SMTP_USER = "<SMTP login>"
$env:AEGIS_SMTP_PASSWORD = "<private SMTP password>"
go run ./cmd/aegis notify --email-to "ops@example.com" `
    --smtp-from "aegis@example.com" `
    --smtp-address "smtp.example.com:465"
```

Поддерживается **implicit TLS SMTP** с проверкой сертификата.
SMTP 587/STARTTLS не включён в текущую реализацию.

**Пример для webhook (PowerShell):**

```powershell
$env:AEGIS_WEBHOOK_SECRET = "<32 or more random secret bytes>"
go run ./cmd/aegis notify --webhook-url "https://hooks.example.com/aegis"
```

Webhook принимает JSON и должен проверять
`X-Aegis-Signature: sha256=<HMAC-SHA256(body)>` и
`Idempotency-Key`. Адрес должен быть публичным HTTPS на порту 443.
Защита запрещает частные и локальные IP, пользовательские секреты
в URL, запросы с query-параметрами и редиректы.

Каналы можно указать **одновременно** в одном процессе, объединив
соответствующие флаги. Секреты передаются только через переменные
окружения сервера, а не Git/React. Маршруты сохраняются в PostgreSQL
без паролей или токенов, до одного адресата на канал.
`--once` выполняет текущие доступные задания и завершает работу,
обычный режим периодически опрашивает очередь (`--poll 3s`).

Отправка **at-least-once**: после падения или потери подтверждения
возможны повторы. У Webhook используйте заголовок
`Idempotency-Key` для дедупликации.

**Важно:** отправка уведомлений автоматическая, но *обнаружение*
инцидентов всё ещё запускается вручную (5.3–5.4); самостоятельного
планировщика проверки условий пока нет. Сообщение не означает,
что сбой был обнаружен без участия оператора.

[ADR 0022](docs/adr/0022-notification-outbox.md).

## Шаг 5.6 — журнал инцидентов и действий операторов

Обновите `develop`, создайте резервную копию БД и выполните
`aegis migrate` с миграционными правами: применяется
**013_activity_journal.sql**. Она добавляет `aegis_activity_log`,
переносит доступные старые события инцидентов и попытки доставки
и устанавливает триггеры атомарной записи новых событий.

Перезапустите Go Dashboard, соберите React из `web/` и перейдите в
**Журнал** (`/activity`). Просматривать записи могут `admin` и
`viewer`; API журнала только для чтения.

Журнал объединяет открытие/подтверждение/эскалацию/закрытие
инцидентов, ручную проверку правил и связи, создание/удаление правил,
смену политики инцидентов, изменение каналов уведомлений и
исходы попыток Email/Telegram/Webhook. Фильтры: категория, действие,
оператор, UUID агента или инцидента, текст названия и даты.
На страницу возвращается до 100 записей (в UI — по 50).

Лог не содержит токены, пароли, SMTP-адреса, URL назначения или
содержимое HTTP-ответов. Важное ограничение: старый
`aegis_admin_audit` для retention/backfill остаётся отдельным,
а события входа/выхода пользователей и отзыва сессий здесь не ведутся.
Журнал предназначен для диагностики и расследования инцидентов,
но пока не является неизменяемым криптографическим архивом.
Для роли чтения БД используйте только `SELECT`, а серверному
писателю выдавайте минимальные права.

Подробнее: [ADR 0023](docs/adr/0023-activity-journal.md) и
[OpenAPI журнала](api/openapi/activity-v1.yaml).

## Этап 5.7 — автономная проверка правил и связи

До 5.7 оценка условий выполнялась вручную через кнопку в панели.
Теперь сервер можно запустить в полностью автономном режиме, но для
обнаружения проблем и доставки уведомлений нужны **два отдельных
долго работающих процесса**:

- `aegis watch` — обнаружение новых инцидентов, восстановлений
  и своевременная (на очередной проверке) эскалация;
- `aegis notify` — отправка созданных outbox-событий по настроенным
  каналам (Email, Telegram или Webhook).

Прежде чем запускать обновлённые процессы, сделайте резервную копию
PostgreSQL и примените миграцию **014**:

```powershell
git switch develop
git pull origin develop
go run ./cmd/aegis migrate
```

Запустите планировщик в отдельном PowerShell (проверки сразу после
старта, далее интервал после завершения предыдущего прохода):

```powershell
go run ./cmd/aegis watch --interval 30s --offline-after 1m
```

Для разового прохода (например, при проверке системы):

```powershell
go run ./cmd/aegis watch --once --interval 30s --offline-after 1m
```

На Linux/macOS, после сборки `aegis`:

```bash
aegis watch --interval 30s --offline-after 1m
```

Оба варианта используют `AEGIS_DATABASE_URL` в окружении
серверного процесса, как и остальные серверные команды.
`--interval` допускает 10 секунд–1 час, `--offline-after`
10 секунд–24 часа (только целые секунды). Обычно 30 сек./1 минута
подходят для начального тестирования, но реальные значения зависят
от частоты heartbeat и допустимой задержки уведомления.

На вкладке **Инциденты → Автоматические проверки** теперь видны:
состояние последнего прохода, число проверенных агентов и правил,
ошибки, время последней успешной проверки и признак устаревшего
статуса. Если процесс завершился и перестал обновлять статус, через
`max(120 с, 3 × интервал)` данные помечаются как устаревшие.

Система использует один PostgreSQL advisory lock на весь проход:
несколько процессов `aegis watch`, направленных в одну БД, не
должны одновременно обходить всех агентов. При падении процесса
соединение и блокировка освобождаются PostgreSQL. По умолчанию
каждый агент проверяется последовательно; неполадка одного агента
не отменяет оценку следующих. Реальные изменения состояния
продолжают атомарно создавать инциденты, записи аудита и задания
доставки — без дублирования прежней бизнес-логики.

**Эксплуатация:** процессы `watch` и `notify` должны непрерывно
работать на сервере под supervisor (systemd, Windows service wrapper
или launchd). Команда `watch` не запускает `notify` автоматически.
Запуск на старте ОС и установочные пакеты входят в фазу 7.
Нет гарантии обнаружения краткого сбоя, исчезнувшего между проверками.

Архитектура: [ADR 0024](docs/adr/0024-automatic-watch.md).

## Фаза 6 · шаг 6.1 — ротация и отзыв токенов агентов

Токен каждого агента можно заменить без создания нового UUID. История
метрик, инцидентов и уведомлений не привязывается к токену.

**Ротация** — команда на доверенной серверной машине, где хранится
закрытый реестр агентов (замените пути и UUID своими):

```powershell
go run ./cmd/aegis agent-token rotate `
  --agents-file "C:\\aegis\\private\\agents.json" `
  --agent-id "00000000-0000-4000-8000-000000000001" `
  --credentials "C:\\aegis\\private\\agent-new.json"
```

Указанный UUID — пример; для ротации требуется настоящий UUID из
серверного реестра. `agent-new.json` **не должен существовать**:
операция не перезаписывает файлы и не выводит токен в консоль.
Содержимое нового файла передайте **только** соответствующему агенту
по защищённому каналу. Перезапустите `aegis receive`, затем запустите
агент с новыми credentials и убедитесь, что heartbeat проходит.
После этого удалите/отзовите старую копию токена в рамках своей
процедуры хранения секретов.

**Отзыв** (доступ прекращается после перезапуска receiver):

```powershell
go run ./cmd/aegis agent-token revoke `
  --agents-file "C:\\aegis\\private\\agents.json" `
  --agent-id "00000000-0000-4000-8000-000000000001"
```

Операции меняют закрытый JSON-реестр. Активный `aegis receive`
сохраняет в памяти прежний снимок реестра, поэтому **обязательно
перезапустите receiver**. Не запускайте ротацию, отзыв и provision
одновременно против одного реестра — пока это однописательский
файл без межпроцессной блокировки. При изменении реестра и
перезапуске сервера возможен кратковременный перерыв приёма метрик.

Перед обслуживанием сделайте резервную копию реестра в
защищённое хранилище. Не размещайте его и JSON с токенами в
GitHub, бэкапах с широким доступом и логах.

Процедура и ограничения: [ADR 0025](docs/adr/0025-agent-credential-lifecycle.md).
