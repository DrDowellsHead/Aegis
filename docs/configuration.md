# Единая конфигурация Aegis — фаза 7.1

Статус: реализованы версионированные профили `agent` (команда `forward`)
и `receiver` (команда `receive`). Это **две роли одного исполняемого файла**,
но не запуск всех серверных служб в одном процессе. `watch`, `notify`,
`dashboard`, `history` пока запускаются отдельно. Службы ОС и развёртывание
сервера будут оформлены в фазах 7.2–7.3.

## Устройство

Шаблон: [aegis.example.json](../configs/aegis.example.json). Создайте
свою копию вне репозитория, например `/etc/aegis/config.json` или в
приватном каталоге конфигурации пользователя Windows. В поле `version`
пока поддерживается только `1`. Можно оставить только `agent` или
только `receiver`, но неизвестные параметры, повторные JSON-ключи и
неправильные типы отклоняются.

Все относительные пути (`private/agent.json`, `public/ca.crt`, `disk`)
разрешаются **от каталога файла конфигурации**, а не от рабочей директории
запущенного процесса. Это важно для systemd, launchd и Windows Service.

```sh
aegis validate-config --config /etc/aegis/config.json
aegis start --config /etc/aegis/config.json --component receiver
aegis start --config /path/to/config.json --component agent
```

`validate-config` проверяет только формат, диапазоны и пути по синтаксису,
не открывает сами сертификаты, секреты, БД или сетевые соединения. Его
результат, если две секции есть, такой:

```json
{"version":1,"valid":true,"components":["agent","receiver"]}
```

Существующие CLI-команды `aegis forward` и `aegis receive` продолжают
работать без конфигурационного файла. При запуске из JSON действуют те же
ограничения, что и при запуске с CLI-флагами.

## Секреты никогда не хранятся в JSON

Секреты передаются через защищённые файлы или переменные окружения.
Для PostgreSQL поддерживаются **взаимоисключающие** способы:

```sh
export AEGIS_DATABASE_URL='postgres://user:password@127.0.0.1:5432/aegis?sslmode=disable'
# ИЛИ, если не задано AEGIS_DATABASE_URL:
export AEGIS_DATABASE_URL_FILE='/etc/aegis/private/database.url'
```

Вариант `_FILE` также доступен для `AEGIS_DIAGNOSTICS_TOKEN_FILE`.
Файлы секретов должны быть обычными, не symlink, максимум 16 КиБ;
на Unix требуются права **0600** (или строже). Единственный завершающий
перевод строки допускается, внутренние переводы строк запрещены.
Пустые файлы, одновременно заданные `NAME` и `NAME_FILE`, а также
нечитаемые файлы блокируют запуск. Ошибка не выводит секрет или путь
к нему. На Windows обычные Unix mode bits не защищают файл — реальные
ACL необходимо отдельно проверить на этапе 7.8.

У агента секретный токен находится в `credentials_file` (проверяемый
приватный JSON существующей системы identity). Для сервера приватный TLS-ключ
и закрытый реестр агентов передаются **только путями** к файлам.
Никогда не помещайте пароли PostgreSQL, токены SMTP/Telegram, содержимое
приватного ключа или строку подключения непосредственно в конфиг.

Пример создания секрета на Unix:

```sh
umask 077
mkdir -p /etc/aegis/private
printf '%s\n' 'postgres://user:password@127.0.0.1:5432/aegis?sslmode=disable' > /etc/aegis/private/database.url
chmod 600 /etc/aegis/private/database.url
```

В production PostgreSQL должен использовать TLS и отдельную роль с
минимальными необходимыми правами. Файл конфигурации должен жить **вне Git**.
Каталог `configs/private/` и локальные `*.local.json` добавлены в .gitignore,
но это лишь защита от случайного `git add`, не замена безопасной установки.
`git add -f` и опубликованная история Git могут обойти .gitignore.

## Границы шага

Сейчас профили запускают agent/receiver. Единая оркестрация служб
`watch`/`notify`/публичной панели, перезапуск по изменению файла,
шифрование секретов, автообновление и права системных служб пока не
реализованы. Установка/реальные ACL/проверка перезапуска — этапы 7.2–7.8.
