# ADR 0010: безопасная очистка телеметрии (retention)

Статус: этап 3.8.

## Цель и время, определяющее срок

До этого каждый подтверждённый Snapshot навсегда оставался в
`aegis_measurements`. Теперь оператор может вручную просматривать
занятое место, выполнять preview очистки и удалять старые данные порциями.

Срок определяется по **received_at** (серверные часы PostgreSQL), а не
по `started_at` из потенциально неточных часов агента. Это защищает
измерения, долго находившиеся в очереди: после доставки у них должен
быть полный срок хранения. Граница строгая:
`received_at < cutoff`, запись ровно на cutoff сохраняется.

Оператор задаёт `--days` в диапазоне 7..3650. Время проверки и cutoff
для одного запуска фиксируются при preview; при очистке порций cutoff
**не пересчитывается**. Записи, сохранённые после начала очистки,
не подпадают под уже установленный cutoff.

## Команды

- `aegis storage`: JSON-отчёт о размере таблицы, индексах,
  суммарном размере таблицы (включая TOAST), размере всей базы,
  количестве строк, оценке мёртвых строк.
- `aegis retention --days 30`: preview **без каких-либо изменений**,
  подсчитывает подходящие строки для всех агентов.
- `aegis retention --days 30 --agent-id UUID`: preview одного агента.
- `aegis retention --days 30 --agent-id UUID --apply`: удаление
  только для выбранного агента.
- `aegis retention --days 30 --all-agents --apply`: явное разрешение
  затронуть всех агентов.

Реальное удаление требует `--apply` и РОВНО одного из
`--agent-id` / `--all-agents`. По умолчанию не более 10 000 строк за
один запуск, не более 500 строк в транзакции; ручные пределы
`--batch-size` (1..2000) и `--max-delete` (1..1 000 000).
`Ctrl+C` останавливает последующие порции; уже закоммиченные
DELETE **не откатываются**. Команду можно безопасно повторить.

## Почему удаление пакетами

Миграция `006_retention_received_at.sql` добавляет индекс по
`(received_at,agent_id,measurement_id)`. Каждая партия выполняет
`WITH candidates AS (SELECT ... FOR UPDATE SKIP LOCKED LIMIT ...),
deleted AS (DELETE ... RETURNING 1)`.
Одно SQL-выражение является атомарной транзакцией PostgreSQL; commit
происходит до сообщения об удалении. `SKIP LOCKED` позволяет
пропускать занятые другой транзакцией строки. Если встретили только
заблокированные строки, команда может остановиться раньше — её можно
повторить после окончания конкурирующей транзакции.

Записи из `aegis_agents` не удаляются: при очистке истории исчезают
только исходные измерения. `last_contact_at` и `last_sample_at`
остаются метаданными агента; последние показатели по истории могут
быть пустыми, даже если состояние ещё известно.

## Место на диске и VACUUM

PostgreSQL использует MVCC: `DELETE` делает строки невидимыми для
новых транзакций, но физические страницы не обязаны сразу уменьшиться.
Обычный autovacuum переиспользует место для будущих вставок, но
`pg_total_relation_size` может не стать меньше. `VACUUM (ANALYZE)
aegis_measurements` улучшает повторное использование страниц и
статистику; НЕ обещает сжатие файла. `VACUUM FULL` переписывает
таблицу и берёт сильную блокировку, поэтому Aegis не запускает его
автоматически. Отдельно существуют WAL, бэкапы, временные файлы и
другие таблицы: размер БД и размер папки PostgreSQL — не одно и то же.

Подсчёт всех строк/устаревших записей может быть дорогим на большой
БД. Команды оператора выполняются вручную, а не на каждый запрос
HTTP API.

## Ограничения и защита от потерь

Retained records могут быть удалены без возможности отката после
COMMIT: **перед --apply нужен актуальный проверенный бэкап**. В
этапе 3.8 архивирование выполняется средствами PostgreSQL
`pg_dump` / `pg_restore`, не выдумывается собственный формат архива.
Разовый резервный файл не заменяет расписание бэкапов и тесты
восстановления.

Нельзя одновременно обещать бесконечную дедупликацию и удалять ключи:
если после очистки агент повторит крайне старое измерение, запись
может появиться снова. Нужна политика горизонта идемпотентности или
отдельные tombstones для долгого срока — за пределами этого этапа.

Также пока нет автоматического расписания retention, архивирования
по разделам таблицы, партиционирования и автоматического мониторинга
роста хранилища. Для production эти функции потребуют отдельного
проектирования, особенно при высокой скорости накопления измерений.
