# ADR 0004: идентификация агента, аутентификация и TLS

Статус: принято, этап 3.2.

## Модель доверия

Каждому агенту выдаётся UUIDv4 и отдельный случайный 256-битный токен.
Provision сохраняет полный токен только в приватном файле агента; на сервере
лежит SHA-256 токена, связанный с UUID. Сервер проверяет метаданные
`authorization: Bearer <token>`, используя сравнение дайджестов без
зависимости времени от совпавших начальных байтов. Токен передаётся
только через TLS; запросы без правильной пары ID + токен отклоняются.

Сервер предъявляет сертификат; клиент доверяет только CA из --ca-cert
и проверяет действительность сертификата и совпадение SAN с адресом
подключения. Запрещены insecure transport и InsecureSkipVerify.
Минимум TLS 1.2. Эта стадия использует токены вместо mTLS;
взаимная TLS-аутентификация может появиться позже.

## Регистрация и хранение

Команда provision создаёт две конфигурации: server agents.json
(хэши токенов) и client agent.json (UUID и токен). Секреты не
выводятся на экран. Повторное создание поверх client agent.json
запрещено. На Unix файлы режима 0600; права на чтение проверяются
при открытии. На Windows доступ регулируется ACL, которые нужно
ограничить учётной записью службы вручную.

Файлы при подготовке нужно передавать по защищённому каналу.
Запускать provision одновременно на один agents.json запрещено:
в этом этапе нет блокировки на уровне нескольких процессов.
Если запись реестра прошла, а создание клиентского файла не удалось,
в реестре может остаться неиспользуемый идентификатор — это
ограничение двух независимых файлов, не транзакция.

Реестр загружается при запуске сервера; после регистрации нового
агента сервер перезапускается. Ротация и отзыв токенов — будущий этап.

## Демонстрационная PKI

Команда cert создаёт краткоживущий сертификат сервера (90 дней)
и локальный корневой сертификат CA. Приватный ключ CA не хранится,
поэтому после переиздания нужно заново распространить CA.
Подходит для локальной лаборатории; для production использовать
управляемый CA и жизненный цикл сертификатов. Указанный --host
обязательно должен совпадать с IP или DNS-именем, к которому
подключается агент. Серверный ключ нельзя публиковать.

## Последующие изменения

Этот ADR отражает принятую модель безопасности этапа 3.2. На этапе 3.3
добавлены дисковая очередь и повторы, а на этапе 3.4 — PostgreSQL,
идемпотентное хранение и подтверждение `durable=true`. Сервер
подтверждает успешный COMMIT базы; агент удаляет запись из очереди
только после такого подтверждения. См. ADR 0005 и ADR 0006.

Ротация токенов и отзыв доверия без перезапуска сервера пока не реализованы.
