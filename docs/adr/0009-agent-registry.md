# ADR 0009: зарегистрированные агенты, активность и состояния

Статус: этап 3.7.

## Зачем отдельная таблица

Файл `agents.json` содержит допущенные ID и SHA-256 токенов, а
`aegis_measurements` — только принятые измерения. Из последней нельзя
узнать о новом агенте, который ещё ни разу не отправил данные.

Миграция 005 создаёт `aegis_agents`: UUID, флаг `registered`,
registered_at, last_contact_at, last_sample_at, last_os, last_arch.
**Никаких токенов и хешей токенов в новой таблице нет.**

При старте `aegis receive` загружает защищённый JSON реестр, после
успешных миграций транзакционно сверяет разрешённые UUID с PostgreSQL,
а уже затем начинает принимать gRPC-запросы. Добавление или исключение
агента в JSON потребует перезапуска receive для применения.
Отсутствующие в JSON UUID помечаются registered=false, но
измерения не удаляются. Reconcile предназначен для одного
авторитетного реестра. Несколько серверов с разными реестрами
для одной базы пока не поддерживаются.

## Семантика активности

Успешная авторизованная новая или повторная gRPC-доставка обновляет
`last_contact_at` **в той же транзакции**, в которой проверяется
идемпотентность измерения. Время задаёт PostgreSQL через clock_timestamp(),
а не потенциально неправильно идущие часы агента.
`last_sample_at` — время исходного измерения, может отставать при
доставке из очереди. Характеристики OS/Arch берутся из самого нового
по started_at снимка; устаревший повтор не должен перезаписывать их.

Состояние выводится из last_contact_at и заданного оператором
`offline_after`:
- unknown — ещё не было подтверждённых контактов;
- online — последний контакт был не более offline_after назад;
- offline — прошло больше offline_after.

Слова online/offline — **оценка активности телеметрии**, не проверка
работы ОС и не постоянное сетевое соединение. При потере gRPC или
продолжительной паузе агента может появиться offline даже если
агент фактически запущен. До добавления отдельного heartbeat
такая неопределённость неизбежна.

При миграции исторические agent_id добавляются как registered=false
с прошлым MAX(received_at) и MAX(started_at): миграция не выдаёт их за
свежие контакты. Только текущий JSON реестр может дать им registered=true.

## API

GET /api/v1/agents?limit=100&cursor=UUID&offline_after=1m

- Доступен только через прежнюю команду `aegis history`;
- Только loopback и отдельный операторский Bearer-токен;
- limit: 1..200, по умолчанию 100; cursor — последний UUID из выдачи;
- offline_after: от 10s до 24h, только целые секунды, по умолчанию 1m;
- сортировка по UUID, `has_more` и `next_cursor` для пагинации;
- данные не содержат секретов. У непосещавших агентов last_contact_at=null;
- 400 для неверных параметров, 401 для неверного токена,
  503 при ошибках хранилища.

Статусы вычисляются при чтении относительно времени PostgreSQL.
Они могут измениться между страницами. Не использовать «offline»
как доказательство отключённой машины или основание для силовых действий.
Дальнейший шаг — отдельный heartbeat и более точная модель unavailable.

## Права PostgreSQL

Для `receive` нужны INSERT/UPDATE в `aegis_agents` и INSERT/SELECT
в `aegis_measurements`. Читающему API достаточно SELECT по таблицам
реестра, истории и журнала миграций. Нельзя использовать один
административный DB-аккаунт для всех сервисов в production.
