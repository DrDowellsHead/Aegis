# ADR 0006: PostgreSQL и подтверждение постоянной фиксации

Статус: реализация этапа 3.4.

## Модель записи

Сервер запускается с AEGIS_DATABASE_URL (секрет не передаётся в аргументах).
Сначала оператор выполняет `aegis migrate`. Миграции встроены в бинарник
через go:embed, последовательно выполняются в одной транзакции под advisory
transaction lock. Сервер отказывается стартовать без требуемой схемы.

Обработчик gRPC сначала проверяет TLS-канал, токен и формат сообщения.
Далее запись `(agent_id,measurement_id,snapshot)` выполняется
через PostgreSQL `INSERT ... ON CONFLICT DO NOTHING`.
PRIMARY KEY(agent_id,measurement_id) атомарно подавляет повторы.
Содержимое хранится как protobuf BYTEA (включая поля отсутствующих метрик),
с SHA-256 канонически кодированного protobuf для проверки повторов.
Если ключ уже существует, сервер читает существующий хеш и подтверждает
**только тождественную запись**; другая нагрузка для того же ID
возвращает FailedPrecondition. Повтор безопасен и после перезапуска сервера.

После успешного подтверждённого PostgreSQL COMMIT в протокол отправляется
`received=true,durable=true`, при повторе `already_stored=true`.
Старый сервер без нового поля durable продолжает отвечать лишь received=true;
новый клиент НЕ удаляет файл на основе такого ответа.

## Очередь агента

Сохранённая запись удаляется из spool только после verified durable ACK.
Файл удаляется через os.Remove, а синхронизация каталога best effort:
после сбоя питания локальная копия иногда может появиться снова, что
безопасно благодаря идемпотентности сервера. Если удаление не удалось,
агент сохраняет ошибку и не утверждает, что очистил очередь.
Потерянный серверный ACK означает повтор с тем же measurement_id.
Файлы, собранные при недоступности сервера, передаются при его восстановлении.

## Ограничения гарантий

Durable ACK предполагает PostgreSQL fsync=on и synchronous_commit != off,
отсутствие аппаратных неисправностей и корректную настройку дискового
хранилища. При недоверенной инфраструктуре, небезопасных дисковых кэшах,
асинхронной репликации или необработанных сбоях оборудования абсолютная
гарантия нулевой потери невозможна. Клиентский spool также не обеспечивает
атомарности против падения питания на всех ОС/ФС.

В этапе 3.4 пока не реализованы ротация токенов, обслуживание схемы
данных при множестве версий, retention, API истории и админ-панель.
Межпроцессная блокировка единственного каталога spool остаётся задачей
отдельного этапа. PostgreSQL нужно резервировать и мониторить.
