# Ветки, теги и GitHub Releases

Коммит — снимок исходников. Ветка — движущийся указатель на последний коммит.
Тег — имя конкретного снимка, например v0.1.0-alpha.1. GitHub Release — описание
выпуска и готовые файлы, прикреплённые к этому тегу.

Рабочий процесс: develop → проверки → pull request в main → тег → черновик Release.
Слияние через merge commit сохраняет отдельные коммиты разработки.

## Когда выпускать

Проверить CI на всех трёх ОС, документацию и сценарий использования. Кросс-сборка
arm64/amd64 не равна испытанию каждой комбинации оборудования. Перед стабильным
выпуском нужны реальные установки на поддерживаемых целевых системах.
Версия v0.1.0-alpha.1 обозначает раннюю предварительную версию.
Не объявлять её полной платформой мониторинга.

## Порядок выпуска (выполнять только при готовности версии)

1. Слить проверенный PR из develop в main.
2. Обновить локальную main и поставить аннотированный тег:

```sh
git switch main
git pull --ff-only origin main
git tag -a v0.1.0-alpha.1 -m "Aegis v0.1.0-alpha.1"
git push origin v0.1.0-alpha.1
```

3. Вкладка Actions: дождаться workflow `Release draft`.
   Он повторяет тесты на Linux, Windows, macOS, проверяет принадлежность коммита
   истории main, собирает шесть архивов, SHA256SUMS и создаёт черновик Release.
4. Открыть Releases → черновик. Проверить файлы, описание изменений и ограничения,
   испытать установку, затем нажать Publish release. Для alpha/beta/rc включается
   признак предварительного выпуска.

Тег сам по себе не является установщиком. Автоматические GitHub-архивы
`Source code` содержат исходники; пользователям нужны архивы `aegis_...`.
Теги опубликованных версий не перемещать. Исправление — новая версия.
При сбое создания черновика сначала проверить, не был ли он уже создан частично:
workflow намеренно не перезаписывает существующий выпуск.

Справка: https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases
