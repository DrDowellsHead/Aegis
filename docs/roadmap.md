# Aegis — полная дорожная карта

Статус: рабочий план, не обещание конкретных сроков.
Ветка `develop` — разработка; `main` — проверенная рабочая версия.
Дополнительные ветки создаются только по необходимости и с понятными именами.
Изменения переносятся в main после CI и проверки. Выпуски — через теги и
GitHub Releases, без переписывания опубликованных тегов.

## Цель

Кроссплатформенная платформа мониторинга: лёгкий агент на Windows, macOS,
Linux; центральный Go-сервер с PostgreSQL; веб-интерфейс для метрик,
пороговых правил, инцидентов и уведомлений; доступная неспециалисту
установка без Go/Python на пользовательской машине.

## Фаза 1. Основа (реализовано)

- CLI, пакеты, версии, логирование, контексты, сигналы, graceful shutdown.
- HTTP healthcheck и разовая проверка URL.
- CI: gofmt, go vet, go test -race, сборка amd64/arm64 для Windows/macOS/Linux.
- Процесс создания релизов, документация по проверке артефактов.

## Фаза 2. Агент (реализовано)

- CPU, RAM, диск и сетевые счётчики; частичные ошибки.
- Локальные команды collect и agent.
- Отличать недоступное значение от реального нуля.
- Потребительские проверки на всех поддерживаемых ОС перед стабильным выпуском.

## Фаза 3. Транспорт и сервер (3.1–3.9 реализованы; далее веб-интерфейс)

- 3.1: versioned protobuf + gRPC.
- 3.2: постоянный ID, per-agent token, TLS-проверки и локальная PKI.
- 3.3: ограниченный spool, retries/backoff, восстановление после перезапуска.
- 3.4: PostgreSQL, миграции, идемпотентное хранение и durable ACK.
- 3.5: HTTP API истории (loopback + отдельный операторский токен).
- 3.6: графические агрегаты по временным интервалам; сохранение проекций
  числовых метрик, пакетный backfill старых protobuf, API временных рядов.
- 3.7: реестр и время последнего подтверждённого контакта,
  оценка online/offline/unknown; не путать отсутствие телеметрии
  с выключенным компьютером. Отдельный heartbeat ещё впереди.
- 3.8: ручная политика хранения (retention), ограниченная пакетная очистка,
  контроль размера БД; резервные копии через pg_dump. Автоматическое
  архивирование и расписание retention — отдельные эксплуатационные задачи.
- 3.9: несекретная административная конфигурация, локальная диагностика,
  транзакционный аудит retention/backfill. Аутентификация операторов,
  аудит миграций и управление учётными записями — следующие задачи.

Критерий фазы 3: агент переживает короткие сетевые сбои, записи
не дублируются, сервер выдаёт историю и пригодные для графиков точки,
административное чтение не становится доступным публично без защиты.

## Фаза 4. Веб-интерфейс (4.1–4.5 реализованы; 4.6 — HTTPS и роли в develop)

- 4.1: выбран React + TypeScript + Vite; OpenAPI-контракт, UX-структура,
  пустой адаптивный каркас без сетевых запросов; публичный gateway не реализован.
- 4.2: локальный Go gateway, вход с отдельным токеном и серверной
  сессией, сводка реестра и статусы, пагинация, обновление.
  Удалённая публикация и TLS/RBAC пока запрещены.
- 4.3: страница агента и графики CPU(avg/min/max), RAM и выбранного
  диска, таблица истории с курсорной пагинацией и частичными ошибками.
  Сетевые скорости отложены до корректного расчёта дельт счётчиков.
- 4.4: произвольный UTC-диапазон до 90 суток, автоматический шаг,
  наведение/выбор временной точки, сравнение с предыдущим периодом,
  корректная обработка часовых поясов и пропусков.
- 4.5: обновления без мерцания, сохранение последнего успешного снимка,
  ограниченные GET-повторы с отменой и тайм-аутом, защита от устаревших
  ответов, Playwright Chromium E2E с подменённым локальным HTTP API.
  Полные E2E против реального Go/PostgreSQL — отдельный будущий тест.
- 4.6: прямой HTTPS/TLS 1.3 с проверкой сертификата и точного Origin/Host;\n  локальные bcrypt-учётные записи, роли viewer/admin, Secure cookies и\n  серверные сессии, отзыв сессий и настройки операторского доступа.\n  Нужны проверка CI, настройка реального DNS/сертификата и отдельные\n  эксплуатационные проверки перед публикацией в интернете.\n  [Безопасность удалённой панели](adr/0017-remote-dashboard.md).

## Фаза 5. Инциденты и уведомления (5.1–5.7 реализованы в develop)

- 5.1: правила порогов CPU/RAM/диска, скользящее окно по started_at,\n  минимальное число измерений, требование свежести, hysteresis;\n  сохранение состояния и ручная оценка из панели (без инцидентов и уведомлений).
- 5.2: отдельный аутентифицированный gRPC Heartbeat (серверный UTC,
  durable ACK), независимый цикл агента, отдельные времена получения
  heartbeat/телеметрии, online/offline/unknown по последнему контакту,
  показ источника в веб-панели. Не путать недоступность канала с
  выключенным компьютером; создание инцидентов — этап 5.3.
- 5.3: инциденты threshold/agent_offline, жизненный цикл
  open/acknowledged/resolved, минимальный журнал переходов,
  транзакционная синхронизация с правилами и оценкой heartbeat,
  API и экран инцидентов с подтверждением/ручным разрешением.
  Проверка условий пока вручную, планировщик и шумоподавление позже.
- 5.4: глобальная настраиваемая политика cooldown (0–86400 сек.)
  и эскалации (60–604800 сек.) в PostgreSQL; подавление повторных
  инцидентов после закрытия, счётчик подавленных проверок;
  единичная эскалация неподтверждённой проблемы до critical при
  следующей ручной оценке. Планировщика и рассылки пока нет.
- 5.5: атомарный PostgreSQL outbox на события opened/escalated/resolved;
  процесс notify с ограниченными lease, 8 попытками и backoff,
  журнал попыток, TLS SMTP, Telegram Bot API, HMAC Webhook с
  защитой от SSRF, счётчики очереди в панели. Оценка самих условий
  по-прежнему вручную; автоматический планировщик — отдельный этап.
- 5.6: единый журнал инцидентов, действий оператора и попыток
  доставки; транзакционные PostgreSQL-триггеры и бэкофилл старых
  событий, серверный actor, API с фильтрами и курсором, отдельная
  страница «Журнал». Админ-аудит retention/backfill и аудит
  аутентификации остаются задачами фазы 6.
- 5.7: автоматический обход зарегистрированных агентов отдельным
  процессом `aegis watch`: проверка пороговых правил и heartbeat
  по расписанию, PostgreSQL advisory-lock для предотвращения
  конкурентных проходов, ограниченные запросы и устойчивость к
  отдельным отказам, сохранение статуса прохода и отображение
  свежести планировщика в веб-панели. `aegis notify` остаётся
  отдельным процессом; автоматический запуск служб — фаза 7.

## Фаза 6. Безопасность, надёжность, эксплуатация (в работе)

- **6.1: жизненный цикл токенов агентов** — штатная ротация и отзыв
  индивидуального 256-битного Bearer-токена без смены UUID или потери
  истории; безопасные закрытые файлы, проверки CLI и обязательный
  перезапуск receiver для применения обновлённого реестра.
  [ADR 0025](adr/0025-agent-credential-lifecycle.md).
- **6.2: PKI и сертификаты** — проверка срока действия, SAN, EKU,
  ключевой пары и цепочки доверия, строгая загрузка PEM CA, двухэтапная
  смена CA через overlap bundle, проверка TLS при запуске gRPC и HTTPS,
  unit/интеграционные тесты. [ADR 0026](adr/0026-tls-certificate-lifecycle.md).
- **6.3: аудит аутентификации и RBAC** — отдельный PostgreSQL
  security ledger для входов, отказов, ограничений, выхода и отзыва
  сессий; блокировка привилегированных действий при недоступном аудите,
  административный API и раздел «Аудит безопасности» в Настройках.
  Роли admin/viewer разделяют управление и чтение в одной инсталляции;
  пер-агентные ACL и многоклиентская изоляция отсутствуют.
  [ADR 0027](adr/0027-security-audit.md).
- **6.4: файловая и межпроцессная безопасность (реализовано в develop)** —
  эксклюзивный системный lock spool до Close, отказ второму процессу;
  резерв свободного места 16 МиБ, строгая реакция на ENOSPC/частичную
  запись и сохранение неподтверждённых измерений.
  [ADR 0028](adr/0028-spool-safety.md).
- **6.5: лимиты и backpressure** — контролируемые ресурсы и
  устойчивость при всплесках телеметрии и уведомлений.
- **6.6: восстановление данных** — backup/restore PostgreSQL,
  реальные тесты восстановления и проверка миграций.
- **6.7: отказоустойчивость** — нагрузочные и chaos-тесты агента,
  сервера, PostgreSQL, потери ACK и сетевых разрывов.
- **6.8: наблюдаемость** — pprof, Prometheus, профилирование памяти,
  SQL-запросов и задержек.
- **6.9: качество выпуска** — supply-chain, анализ зависимостей,
  минимальные права, определение SLI/SLO и пределов нагрузки.

Нумерация 6.1–6.9 фиксирует направления работ, но не заменяет
технические критерии готовности и тестирование на реальных машинах.

## Фаза 7. Продукт и релизы

- 7.1: единая конфигурация agent/server, поддержка секретов без git.
- 7.2: агенты как Windows Service, systemd service, launchd daemon.
- 7.3: Docker Compose для серверной части, схемы БД и конфигурации.
- 7.4: Windows installer, macOS package, Linux пакеты/службы.
- 7.5: обновление и миграция конфигураций без потери данных.
- 7.6: SHA256SUMS, подпись артефактов, notarization/signing где требуется.
- 7.7: инструкции установки, удаления, troubleshooting, security.md.
- 7.8: alpha -> beta -> release candidate -> стабильный GitHub Release.

Каждая фаза может иметь промежуточные alpha-релизы. Нельзя считать
кросс-компиляцию эквивалентом тестирования установки на реальных устройствах.

## Что намеренно не добавляем без обоснования

- Redis, Kubernetes, сложный брокер сообщений и дополнительные микросервисы
  не являются обязательными для первой рабочей версии.
- Сначала измеряем нагрузку и только потом добавляем кэш, очереди или
  разделение сервера на процессы.
- Обещания «exactly once» для сетевого транспорта заменяем
  проверяемой at-least-once доставкой с идемпотентной фиксацией.
